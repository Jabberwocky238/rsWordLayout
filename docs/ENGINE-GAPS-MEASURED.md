## 先说这批数是在哪棵树上量的

`main` 已把 `engine.rs` / `measure.rs` 合并进 `layout.rs` + `font/`，并自带 `oracle.rs`。

出口已经补上了（`oracle_json` + `layout-trace`），所以现在可以在 `main` 上直接复量。

## 1 Word 侧结论

这些是关于 Word 本身的读数。范围限定写在同一处，别只抄结论（方法 §7.6）。

| | |
| --- | --- |
| 夹具 | **1 份**，`MR1-BREAKS`（11 页、15 段、278 个字形）＋ `MR7-LEADER-SPAN`（2 页、2340 个字形） |
| 采集 | **折算既有采集**（`provenance: ADOPTED`），Word for Mac 16.112.26083020 |
| 平台 | **Mac**。§6.6：Mac 与 Windows 是两套字体度量，**不能互相替代** |
| 字体 | Liberation Serif / Sans，12pt 为主 |

**未测**：CJK、表格、脚注、页眉页脚、编号、制表位、跨批次重复性、Windows 侧的任何一条。

### W-1 纵向落在 1/300 英寸的栅格上（证据强）

Word for Mac 把字形基线放在 **0.24pt = 1/300 英寸**的栅格上。
两份夹具、**56 个**不同的基线 y，**56/56 全部**是 0.24pt 的整数倍；
同批数据里 x 坐标只有 **1/85** 落在该栅格上——所以这是纵向独有的，不是坐标系的假象。

### W-2 行高与基线怎么落到栅格上（**回测，证据薄**）

下面两条是**拿数据凑出来的**，按方法 §7.5 标「回测」，**不当独立检验**：

- 行高 = 自然行高四舍五入到栅格：只对上 **2** 个点（12pt → 13.68pt，13.92pt → 16.08pt）；
- 基线 = 行高 − 量化后的 descent：只对上 **1** 个点（13.68 − 2.64 = 11.04）。

要证实或推翻，需要一份**专门变字号与字体**的夹具，本仓库还没有。

### W-3 横向是字体的精确推进量，且**不做字距调整**

Liberation Serif 12pt 实测：`B` = 8.0040pt、`P` = 6.6720pt、`[` = 2.6374pt，
就是字体 `hmtx` 的值。数字恰好 6.0000pt（0.5 em）是**巧合**，不是「西文都 0.5 em」。

而且 Word **没有应用 GPOS 字距调整**：`B11` 一行里两个 `1` 各 6.0000pt，
而 Liberation Serif 的 `1`+`1` 是有一对 kern 的。这与 OOXML 的 `w:kern` 语义一致——
它给的是「字号大到多少才启用字距调整」，不写或写 0 就是**不调整**。

### W-4 分节边界后那一行，行高多了正好一格（n=1，未解）

`B09 → B10` 的行距是 **13.92pt**，而其余所有同字体同字号的行距都是 **13.68pt**——
差 0.24pt，正好一个栅格单位。B09 带 `sectPr kind=nextPage`，B10 带 `continuous`。

**只有 1 个实例，不下结论**，记成具名未决项（§7.7：要么留在文本里，要么转成未决项，
没有第三种）。

### W-5 `w:sectPr/w:type` 说的是这一节自己怎么开始

`nextPage` / `evenPage` / `oddPage` 起新页，`continuous` 不起。
该夹具 5 个节的页归属逐条相符（**5/5**）。

## 2 引擎侧缺口

### 在当前 `main` 上实测（2026-09-17）

用 `layout-trace` 出轨迹，`wm selfcheck` 查契约、`wm compare` 对 Word。
`selfcheck` **不需要 Word 采集**，5 份夹具全跑：`mr1`（MR1-BREAKS）与仓库自带的
`breaks` / `wrap` / `sample` / `complex`。

| 查的是 | 结果 |
| --- | --- |
| 与 Word 比（MR1） | **结构全程对上：11 页 = 11 页，20 行 = 20 行，264 对字形全部配上** |
| 源字符区间 | ~~5/5 份夹具不合契约~~ → **已修**（E-1），5/5 通过，段边界与 Word 逐段相符 15/15 |
| 自报终止符字形数 vs 实画 | ~~MR1 上 3 行自相矛盾~~ → 随 E-3 一并消失（E-2） |
| U+FFFC 被当真字形画出 | ~~mr1 8 / breaks 1 / wrap 1~~ → **已修**（E-3），5/5 份夹具归零 |
| 行记账粒度 | ~~5 份里 4 份不合契约~~ → **已修**（E-4） |

#### E-1 源字符区间记的是**段内**偏移，不是全篇偏移 —— **已修**

`oracle.rs` 写的是「单位 UTF-16，与 rsword 的坐标流一致」，而 Word 的 `Range.Start/End`
是**全篇连续**的。实测 `sourceStart` 回到 0 的次数正好等于段落数：

| 夹具 | 回到 0 的次数 | 段落数 | 最大 `sourceEnd` |
| --- | ---: | ---: | ---: |
| mr1 | 15 | 15 | 22（篇长 287） |
| breaks | 3 | 3 | 11 |
| wrap | 7 | 7 | 219 |
| sample | 21 | 21 | 445 |
| complex | 42 | 42 | 377 |

这条**比看上去严重**：段内偏移与全篇偏移长得几乎一样（都是小整数、都单调），
比较器会以为两边在说同一件事。而按读序配对的校验全靠这个区间，区间对不上，
配对就没有依据（§3.2）。

**修法**：`break_paragraph` 收一个 `source_base`（本段首字符的全篇下标），
主循环按「本段 UTF-16 长度 + 1 个终止符」推进游标。同时补上一处漏账——
换行处被 `trim_start_matches(' ')` 吃掉的空格**在源侧仍然占位**，
不记进游标会让本段后续片段整体前移，而那种错在几何上看不出来。

**核过**：MR1 夹具上引擎的段边界与 Word 的 `Document.Paragraphs` **逐段相符 15/15**
（引擎不画段落终止符，故止点为 Word 段末 −1）；最大 `sourceEnd` 286，Word `endOfContent` 287。
回归测试 `crates/core/tests/source_offsets.rs` 5 条，**在修前的代码上 5/5 全红**。

#### E-2 引擎自报的终止符字形数，和它自己画出来的对不上 —— **随 E-3 消失**

轨迹里每行既有 `terminatorExpectedGlyphs`，又有实际画的字形。**两个数出自同一份记录**，
对不上就是自相矛盾，不必等 Word 判：

```
p0 L1 PAGE_BREAK_MID_PARAGRAPH：自报 0 个，实画 1 个（glyphId 2323）
p0 L3 PAGE_BREAK_MID_PARAGRAPH：自报 0 个，实画 1 个（glyphId 2323）
p0 L5 PAGE_BREAK_MID_PARAGRAPH：自报 0 个，实画 1 个（glyphId 2323）
```

（自检只能抓终止符独占一行的情形；`WRAP` 行整行都是正文，分不出来，故这 3 条是下界。）

#### E-3 U+FFFC 占位符被当成真字形画出去 —— **已修**

glyphId 2323 在 Liberation Serif 里就是 **U+FFFC**（对象替换符），12pt 字号下 advance **12.0pt**。
rsword 为每个 `w:br` 在 `run.text` 里放一个 U+FFFC，引擎把整串交给整形器，于是它被画了出来——
Word 那边**一个都没有**。

| 夹具 | 画出次数 | 凭空占掉 |
| --- | ---: | ---: |
| mr1 | 8 | 96.0pt |
| breaks | 1 | 12.0pt |
| wrap | 1 | 12.0pt |

每出现一次，该行其后所有字形的原点整体右移 12pt。

**修法**：在断行处按 U+FFFC 切分 run 文本——它占 1 个源字符位（游标照走），
但不产生片段、不占宽度，因而也到不了绘制层。

**必须在断行处切，不能只在绘制层滤**：只滤绘制，行宽照样把它算进去，
而那种错在轨迹里**看不出来**——字形没了，但断行位置已经被它带偏。
占位符会夹在文字中间（实测 `'分页符之前￼分页符之后'`），所以不能按「独立成 run」处理。

**核过**：5 份夹具 U+FFFC 画出次数全部 8/1/1/0/0 → 0；字形总数正好减去占位符个数
（mr1 272 → **264**，恰好等于 Word 的 278 减去 14 个终止符字形）。
回归测试 `crates/core/tests/placeholder.rs` 5 条，**在修前的代码上 5/5 全红**。

#### E-4 「行」这一层被 run 切碎 —— **已修**

`LayoutRecord::from_paint` 把每条 `DrawCmd::DrawGlyphs` 当一行，而绘制指令是**按 run** 出的。
MR1 上 Word 排 20 行、引擎报 29 条记录；差额正是一行里的多个 run
（`'B04 before'` + 分页符 + `'after'` → 3 条记录）。上下标同理
（`'B13 super'` + `'[sup]'` → 2 条）。

行层配对必然对不上，而且失败**看起来像「引擎少排了行」，其实是记账粒度错了**。

**修法**：`TextFragment` 与 `DrawCmd::DrawGlyphs` 带上本页内的行号，
`LayoutRecord::from_paint` 按它把同一行的多条指令合回一条记录
（源区间取并集，终止符取行末片段的真实值）。

**另一半是空行**：空行不产生片段，也就没有任何绘制指令，于是根本**没有行记录**——
而 Word 是给空行一条行记录的（独占一行的分页符、空段落都有）。这种缺失在比较器里
同样表现为「引擎少排了行」。已让 `place_line` 为空行也产出一个空片段。

**核过**：MR1 29 条记录 → **20 行 = Word 的 20 行**；p6/p7 的分页行、p10 的上下标行
都不再错位。回归测试 `crates/core/tests/line_records.rs` 6 条，退回后分别有 3 条
（合并）与 2 条（空行）变红。

#### E-5 手动分页符的位置三分，全部塌成 `MID_PARAGRAPH`

MR1 的 8 个分页符本应分三类：3 个紧跟段落标记（`BEFORE_MARK`，画 1 个空格）、
3 个段中（`MID_PARAGRAPH`，0 个）、2 个行首独占（`OWN_LINE`，0 个）。
引擎 8 个全报 `MID_PARAGRAPH`——**5/8 分类错**。

#### E-6 手动分页符不翻页 —— **已修**

MR1 Word 11 页、引擎 1 页。他们自己的 `breaks.docx`（1 个手动分页符，应排 2 页）
也只排出 1 页。y 游标分页本身是好的（`sample` 排 2 页、`complex` 排 6 页），
缺的是 `w:br w:type="page"` 到翻页动作的那一步。

**难点不在翻页，在分辨**：占位符 U+FFFC **不区分种类**——分页符、软回车、行内图
在 run 文本里是同一个字符，种类只在 `segments[].kind` 里。分不出来的后果是双向的：
要么该翻页的不翻，要么**一张图把文档劈成两页**（`wrap.docx` 的占位符正是行内图）。

**修法**：`Run` 增一个 `placeholders: Vec<PlaceholderKind>`，按文档顺序与文本里的
占位符一一对应，由桥接层从 `segments[].kind` 读出来。排版在切分处按种类决定
收行／翻页。个数对不上时整体退回 `Object`——保守方向，**宁可少一次分页，
也不凭空造出一次**。

**核过**：`breaks.docx` 1 → **2 页**（正确）；MR1 8 个分页符 1 → **9 页**；
`wrap.docx` 的行内图**没有**误触发分页（仍 1 页）；`sample` / `complex` 不受影响。
回归测试 `crates/core/tests/page_breaks.rs` 7 条，**把修改退回去后 4 条正向断言全红**
（3 条负向断言两边都绿——它们防的是反向的错）。

### 几何层：接真度量之后（当前 `main`，2026-09-17）

纯文本页 p0–p9（226 个字形），三种配置逐步收敛：

| 配置 | Δx max | Δy max |
| --- | ---: | ---: |
| 桩度量 | 0.1504 | 1.4400 |
| 真度量 | 0.1504 | 0.3400 |
| 真度量 ＋ Mac 纵向栅格 | 0.1504 | **0.1900** |
| ＋ 推进量只取一次整（G-8a） | **0.0244** | 0.1900 |

逐行看 Δy 就更清楚了：**15 行里 14 行是 +0.01 / +0.03pt**，那正是 twip 与
0.24pt 栅格通约不了的地板（G-8）；剩下 **1 行 −0.19pt**，是分节边界那条
**未解**的行高异常（W-4）。

Δx 在换度量时三种配置相同，因为字形位置来自 paint 的整形器，布局度量只管断行与行高；
它的 0.1504pt 是取整时机的问题，已由 G-8a 修掉，现在是 **0.0244pt = 半个 twip**，
整数 twips 下的硬地板。

Δy 的 0.19 只来自那 1 行未解的分节边界异常（W-4）；其余 14 行是 +0.01 / +0.03pt，
那是 G-8b 的逐行累积，尚未修。

### G-1 `w:br w:type="page"` —— 见上面的 E-3 / E-5 / E-6

`bridge.rs` 读得到 `breakKind`，`oracle` 侧也有 `PageBreakPosition` 的三分，
但**三件都没接上**：不翻页、位置三分塌成一类、占位符被画出来。

### G-2 分节起始翻页 —— **已修**

（此前本文一度写「已覆盖」，是错的：`bridge.rs` 处理段内 `sectPr` 只是为了定终止符，
`sections[].blockRange` 根本没被读。）

**修法**：读顶层 `sections[]`，把 `kind` 为 `nextPage` / `evenPage` / `oddPage` 的节的
`blockRange[0]` 标成 `page_break_before`。按**块下标**查，不是段落序号——
非文本块（表格、绘图）会被跳过，拿段落序号查就会错位。

`nextColumn` **不当成换页**（本版不实现分栏，当成换页会凭空多出页）；
`evenPage` / `oddPage` 只当成「起新页」，**落在偶／奇页的那一层未实现也未测**。

**核过**：MR1 9 → **11 页 = Word 的 11 页**。回归测试
`crates/core/tests/section_breaks.rs` 7 条，**退回后 4 条正向断言全红**。

### G-3 段落标记与分页符的字形 —— 14 / 278 个字形

Word 为每个终止符画一个空格字形（§4）：`PARAGRAPH_MARK` 11 个 ＋
`PAGE_BREAK_BEFORE_MARK` 3 个 = **14**，与实测缺口逐位相等（278 − 264 = 14）。

要不要让引擎真排出这个字形是**未决项**：它是零墨迹的空格，但**占宽度**，
因而影响两端对齐的空隙分配与行尾光标位置。上表的几何数都是把这 14 个
**显式排除出验收范围**之后得到的（§8 的处置，`--exclude-rule`，不是放宽容差）。

### G-4 真度量 —— **已修**

`font/simple.rs` 是桩（`ascent 0.8 em、descent 0.2 em`，西文一律 0.5 em）。
新增 `font/real.rs` 的 `RealMetrics`：横向走 `FontRegistry::shape_text`
（按 Word 的槽规则选 face、rustybuzz 整形），纵向读字体的 `hhea`/`OS/2`。

断点提取成 `font/linebreak.rs`，**两种度量共用一套**——否则换度量之后的差值里
会混进断行策略的变化，分不出是哪一边错。

**顺带修掉字距调整**：`rustybuzz::shape(&face, &[], buf)` 不传 feature 时
**默认开**，而 OOXML 的 `w:kern` 给的是「字号大到多少才启用」，不写即**不调整**。
实测 `B11` 一行里两个 `1` 有一对 kern，Word 没用，该行从第二个字形起整体偏 **0.45pt**。
`FontSpec::kerning` 默认 false，`bridge` 从 `w:kern` 读阈值。
修掉后纯文本页 Δx max 从 **0.4744 → 0.1504pt**。

### G-7 `vertAlign` 与 `w:position` —— **已修（缩放与抬升）**

上标、下标、抬升 run 原先全都按正文排。抬升 run 页（p10，38 个字形）max|Δx| = 8.8684pt，
比其余所有页高一个数量级。

**比例是从真 Word 量出来的，不是字体给的。** 实测（Liberation Serif 12pt）把两者分得很开：

| | 字体 OS/2 说 | Word 实际用 |
| --- | ---: | ---: |
| 字号 | 0.6499 em（7.7988pt） | **0.66 em（7.92pt）** |
| 上标偏移 | 0.4531 em（5.4375pt） | **0.34 em（4.08pt）** |
| 下标偏移 | 0.1431 em（1.7168pt） | **0.08 em（0.96pt）** |

**所以不要「改进」成读 `ySuperscriptYSize`**——那看着更正确，却与 Word 对不上。
证据强度 **n=1**（一种字体、一个字号），按 §7.5 属**回测**，需要专门变字号与字体的夹具。

`w:vertAlign` 与 `w:position` 是**不同机制**：前者同时缩字号并挪基线，
后者（半点，可负）**只挪基线不改字号**——实测 `w:position=8` 那段仍是 12pt。

**核过**：p10 的 max|Δx| 8.8684 → **5.3517**；上标行、下标行的基线误差降到
−1.44 / −1.32pt，与纯文本页**同一水平**（那是 G-5 的基线偏移，不再是 G-7）。
抬升量本身准到 0.03pt。回归测试 `crates/core/tests/vertical_align.rs` 6 条，
退回后 4 条正向断言全红。

**还有一条单位天花板**：0.66 × 12pt = 7.92pt = **15.84 半点**，而
`FontSpec::size_half_points` 是整数半点，**表达不了**；这里取最近的 16 半点（8pt，差 +0.08pt）。
与 `Twips` 对不上纵向栅格是同一类问题（G-8）。

### G-9 含抬升 run 的行，行高会变 —— **未解（n=1）**

p10 上 `B14 → B15` 的行距是 **18.0pt**，而同页 `B13 → B14` 是 13.68pt——
B15 带 `w:position=8`。Word 把含抬升 run 的行**加高了 4.32pt**，引擎没有，
于是该行基线差 **−5.52pt**（其余行只差 −1.44）。

试过的几种算法都对不上：`ascent + rise` 再按栅格量化给 17.76pt，不是 18.0pt。
**只有 1 个实例，不拟合**——记成具名未决项，要一份专门变抬升量与字号的夹具才能定。

它是 p10 上 max|Δy| = 5.52pt 的**唯一**来源；除掉那一行，p10 的 Δy 与纯文本页一致。

### G-8 `Twips` 的分辨率 —— **横向已拆掉地板，纵向仍有累积**

分三层，前两层是**取整时机**（可修），第三层才是单位本身（架构选择）。

#### G-8a 横向：逐字形取整会沿行累加 —— **已修**

`shape_with_face` 原先给每个字形各取各的整。Word 给 `e` 5.3280pt、引擎给 5.3500pt
（差 1 twip），到第 20 个字形攒到 3 twips（0.15pt）。**行首对得上、越往右越偏**，
看着很像度量不准——其实度量是对的，是取整时机错了。

**修法**：未取整的累计推进量留在 f64 里，**推进量取相邻取整位置之差**。
于是任意前缀和都恰好等于「精确累计值取整」，位置不漂；单个推进量仍是整 twips，
`ShapedRun` 的契约不变。

**核过**：纯文本页 Δx max **0.1504 → 0.0244pt**——半个 twip，整数 twips 下的硬地板。
回归测试 `crates/core/tests/advance_accumulation.rs`，期望值**从字体表独立算**。
（那个「硬地板」后来也拆了，见 G-8d。）

> 第一版测试拿 `measure(前缀)` 当期望，两边共用同一条求和路径，
> **在有缺陷的旧代码上照样全绿**——等于自证（§7.2：设计案例不能兼作检验）。
> 换成独立期望后，旧代码上 2 条核心断言立刻变红。

#### G-8b 纵向：逐行取整会沿页累加 —— **已修**

同一个毛病换个方向：栅格上的行高精确值是 **273.6 twips**，落到整 twips 是 274，
每行多 0.4 twip；一页 40 行就攒到 0.8pt。

`TextMetrics` 是 `#[repr(C)]` 且有测试把大小 16 与字段偏移钉死，**不能加字段**。
改用**增量的 trait provided method** `FontMetrics::natural_height_fine`，
单位 1/7200 英寸（twips 与 1/300 英寸栅格的公倍数——两者只在这里通约）：
默认实现由 twips 换算（不提供额外精度），`RealMetrics` 覆盖它且**不做整形**
（行高只取决于纵向量，比 `measure` 便宜）。布局的纵向游标改走精细单位，
只在落位与判断时换回 twips。

**中途踩到一个更隐蔽的**：`line_height_fine` 末尾的「内容下限」`max(content)`，
而 `content` 是取整后的 `ascent + descent`（栅格上 221 + 53 = 274 > 273.6）——
拿它 `max` 精确值，就把刚避开的舍入误差**每行灌回来一次**。
下限改在整 twips 的粒度上比较才对。这条是合成测试抓出来的：第 2 行就漂了 0.8 twip。

**MR1 夹具上看不出效果**：它每页最多 3 行，累积还没显出来，逐行 Δy 仍是
+0.01 / +0.03pt（那来自 ascent 本身的取整，不是累积）。
所以这条由 `crates/core/tests/line_height_drift.rs` 的**合成多行输入**验证，
不拿实测夹具充数。

#### G-8d 横向：整 twips 这个地板本身 —— **已修**

G-8a 修的是「怎么在整 twips 里分配舍入」，前提是**落位必须是整 twips**。
量具把这个前提否掉了：`accumulation` 那份采集里，**引擎 1340 个推进量全部**落在整 twips 上、
**Word 一个都没有**（`docs/MEASUREMENT-BACKLOG.md` 的 H2）。前提错了，分配得再匀也没用。

**为什么横向不学纵向用定点。** 纵向能用 1/7200 英寸，是因为 Word 的基线落在
1/300 英寸上，1/7200 是它与 twips 的公倍数——那是个能整除的目标。横向没有这种目标：
Word 的推进量落在 **1/10000 em** 上，而 em 随字号变，没有哪个固定的绝对单位能整除它
（8.5pt 下 1/10000 em = 0.00085pt，20pt 下是 0.002pt）。既然取多细的定点都要留残差，
就不取——把精确值一路留在 `f64` 里，只在最后出数时落一次。

**改法**（与 G-8b 同一套手法，方向换成横向）：

| 层 | 原来 | 增补 |
| --- | --- | --- |
| 度量 | `TextMetrics::advance`（twips） | `FontMetrics::advance_pt`（provided method，点） |
| 整形 | `ShapedRun::x_advance`（twips） | `ShapedRun::x_advance_pt` |
| 断行 | `cur_w`（twips） | `cur_w_pt` —— **断行仍走 twips**，只有落位读精确值 |
| 落位 | `TextFragment::x`、`PositionedGlyph::x` | `x_pt` |
| 出数 | `GlyphRecord::origin_x` | `origin_x_pt`，`oracle_json` 改用它 |

`TextMetrics` 是 `#[repr(C)]` 且被测试钉死了大小与偏移，所以精确值同样走 trait 的
provided method 而不是加字段——与 `natural_height_fine` 一个道理。

**核过**（`fixtures/accumulation.docx` vs `captures/accumulation-2026-09-17`，1340 个字形）：

| | 修前 | 修后 |
| --- | ---: | ---: |
| **行末** \|Δx\| max（240 行） | 0.0247pt | **0.00002pt** |
| 行中 \|Δx\| max | 0.0400pt | 0.0225pt |
| 行中 \|Δx\| 中位 | 0.0121pt | **0.0031pt** |
| 全部 \|Δx\| 中位 | 0.0200pt | **0.0004pt** |

**行末那一列才是判据。** 行内的 Δx 不全是引擎的：Word 导出的 PDF 把字形宽度写成
**1/1000 em 的整数**（22 份采集包、17231 个字形，零例外），每个 run 再配一个 `Tc`
把总量补回来——所以行内带量化噪声，到行末才对齐。1340 个字形**全部**落在
`\|Δx\| ≤ 0.0005 × 字号 × 行内序号` 内。那 0.0225pt 是**通道的分辨率**，不是引擎排错了
（`MEASUREMENT-BACKLOG.md` 的 H6）。

**别的夹具上也变好，但最大值没变**：`indent-align` 逐位相等的比例 9.5% → **28.2%**、
中位 0.0231 → **0.0078pt**；`hbox` 3.1% → **5.2%**。两者的 max（0.50pt / 48pt）纹丝不动——
它们的大头是对齐与两端对齐（H3b / H3c / H3d），跟推进量无关，这条修不到。

#### G-8c 单位本身

布局单位是 `Twips`（i32，1/1440 英寸 = 0.05pt），Word 的纵向栅格是 1/300 英寸 = 0.24pt
= **4.8 twips**。栅格点根本落不到整 twips 上，两者只在 **1/7200 英寸**上才通约。

G-8a / G-8b 修掉的是**取整时机**，G-8d 修掉的是横向那个地板本身。
剩下的是：`Twips` 仍是布局的**主**单位，精确值是挂在旁边的一条支路
（`x_pt` / `baseline_fine`）。**只有比对与出数读支路**，绘制、命中测试、GPU 顶点
仍走 `Twips`，那里还留着半个 twip（0.025pt）的地板。
要让整条链都精确，得动 `#[repr(C)]` 的顶点数据与整个 GPU 链——
**那是架构层面的选择，不是调参**。

（上表 Δy max 0.19 的**唯一**来源是 W-4 那一行；除掉它，Δy max 就是 0.03pt。）

### 两条实现上的坑，都是量出来才发现的

- **逐字形取整会沿行累加**：推进量要在 f64 上累加，落位时取一次整。
- **量化时 ascent 与 descent 分别取整，和会偏出栅格一整个 twip**，且逐行累积：
  `round(278.4 − 52.8) + round(52.8) = 279`，而 `round(278.4) = 278`。
  行高要只取整一次，差额全部归 ascent。

## 4 量具自己被改过的地方

诚实清单——这些不是引擎的缺口，是量具的：

- **计数模型把分节符当成了段落标记**。整页预期 62、实测 60，闸门拦下，没有串行。
  根因：`\r` 与 `\x0c` 都只占 1 个字符位，只核长度的验证对此不敏感（§7.2）。
  已改为从 `document.xml` 逐字符标注构造，并在 `verify()` 里**声明它核不了终止符身份**。
- **分页符位置只看行内上下文**，把「段中」误判成判不了。已改为同时看段落与行。
- **证否条件 F4 真的触发过**：计数模型说判不了的行，被 §3.2 前置检查的巧合相等
  盖过去判成 OK。已修（`pairing.pair_line`），留了回归测试。
- **自检的第一版误报了 125 行**：`WRAP` 表示源侧没有终止符字符，整行都是正文，
  拿它去判「终止符该画几个」会把单字符正文行当成矛盾。看数据才发现，已修并留了回归测试。
- **新增 `decompose()`**：按「每行第一个字形」拆差值。它前面没有推进量可累积，
  所以 Δx 只反映行起点、Δy 只反映基线。这条拆法当场排除了「查缩进」整条路——
  首字形 Δx 在桩度量下就已经是 0.0000pt（18/18 行逐位相同）。
