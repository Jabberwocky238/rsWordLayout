# 预注册：CJK 纯文本，第一批

日期 2026-09-18。**判据在采集之前写死**（§7.1）。夹具 `fixtures/cjk-plain.docx`，
sha256 `07dea76d27bb…`，由 `tools/measure/make_cjk_fixture.py` 生成。

## 0 为什么这是第一批

本仓库此前 22 份采集包、**17231 个字形里一个 CJK 字形都没有**（逐份查过）。
`MEASUREMENT-BACKLOG.md` 把「CJK 断行」列在范围外，`ENGINE-GAPS-MEASURED.md` 写「未测」。
引擎那边 `font/linebreak.rs` 有一整套按字断行与行首禁则，**从未被任何读数碰过**。

`fixtures/plain.docx` 不能用：它的 `w:eastAsia` 是 **SimSun**，本机 Word 列不出
（`wm preflight` 实测 `SimSun: false`），采下去就是字体替换，而替换在几何上不可见（§6.2）。
本批改用 **Songti SC**，在 Word 自报的 1614 个字体名里。

## 1 量具在 CJK 上少了哪条通道 —— 先说清楚

| 通道 | 拉丁 | **CJK** |
| --- | --- | --- |
| PDF 逐字形几何 | 有 | **有**，与脚本无关 |
| 行划分（行号扫描，§2.1 第三通道） | 有 | **有**，与脚本无关 |
| 按读序配对（§3.2） | 有 | **有** |
| **配对后的身份核对（§3.1）** | 有 | **没有**——ToUnicode 对 CJK 子集无效，方法原文明写 |

**后果要写在结论里，不能省**：§3.2 那条前提「PDF 内容流的绘制顺序 = 源字符顺序」，
在拉丁批次上有身份核对当事后交叉验证，**本批没有**。所以本批的一切判定都附带
「前提未经独立核对」这条限定。**这不是可以靠多采几份补上的**，是这条通道本身不存在。

另有一条**间接**的核对可用，本批会做：Songti SC 里拉丁字符与中文字符都有，
夹具的标点是全角（在 CJK 区），**若配对串了行，行内字符数会对不上**（§4 的计数模型仍然可用）。

## 2 预测

夹具：四页行距组（10.5 / 12 / 16 / 22pt，每页 6 个两字短段落）、
两页断行组（12pt 长段落，一段无标点一段密布禁则标点）、一页段落标记组。

| | 预测 | 分母 |
| --- | --- | ---: |
| **Z1** | 每条基线都是 0.24pt 的整数倍（V1 的 CJK 检验） | 全部基线 |
| **Z2** | 行距 = **N7**：`(hhea.asc − hhea.desc + hhea.gap)/upem × 字号 × 1.3` | 4 个字号 |
| **Z3** | 每个段落标记画 **1 个**空格字形（C1 的 CJK 检验） | 全部段落 |
| **Z4** | 每行第一个字形的 x = **72.0000pt**（左边距 1440 twips；H3a 的 CJK 检验） | 全部行 |
| **Z5** | Word 每行的**源字符数**与引擎逐行相同（CJK 按字断行的第一次检验） | 断行组全部行 |
| **Z6** | 断行组里**没有任何一行**以行首禁则字符开头 | 断行组全部行 |

**Z2 的预测值写死在这里**（Songti SC：upem 1000、hhea 1060 / −340 / 0 → N1 = 1.4000 em；
`OS/2.ulCodePageRange1 = 0x40000`，第 18 位=简体中文置位 → 按 N7 取 ×1.3）：

| 字号 | N1 | **N7 = 预测行距** |
| ---: | ---: | ---: |
| 10.5pt | 14.7000 | **19.1100pt** |
| 12.0pt | 16.8000 | **21.8400pt** |
| 16.0pt | 22.4000 | **29.1200pt** |
| 22.0pt | 30.8000 | **40.0400pt** |

容差同 `PREREG-2026-09-18-auto-line.md` §2：`0.24 / (行数 − 1)`。

**Z2 是 N7 的第一次独立检验**：N7 是在拉丁采集上回测出来的，Songti SC 不在那 32 种字体里，
本夹具也不在那 9 份采集包里。**但它检验不了「按代码页判」还是「按脚本判」**——
本机没有能分开这两者的字体（「拉丁字形、声明东亚代码页」全机只有 Brush Script MT 一个，
就是回测数据里那个；「画得了 CJK、不声明东亚代码页」**一个都没有**）。
所以 Z2 成立只说明 N7 在一个新东亚字体上仍然对，**不说明那个 1.3 是代码页带来的**。

**Z6 的对照**：`wrapPlain` 段不含任何标点，`wrapKinsoku` 段密布禁则标点。
若 Z6 在两段上表现相同，说明 Word 根本没有把标点推到行首过，那这一条**判不了**
（不是成立），要换一份把标点精确摆在换行点上的夹具。

# 5 判定（2026-09-18，采集之后写）

采集包 `captures/cjk-plain-2026-09-18/`。Word 7 页 / PDF 7 页 / 301 个字形 / 33 行，
行分母 **33 成立、0 不成立、0 判不了**。字体核查 PASS（PDF 里只有 `Songti SC`）。

| | 判定 | 读数 |
| --- | --- | --- |
| **Z1** 基线在栅格上 | **成立 301/301** | V1 在 CJK 上同样成立 |
| **Z2** 行距 = N7 | **成立 4/4** | 见下表 |

## 5.1 Z2：N7 在一个没见过的字体上预测准了

| 字号 | 预测（判据里写死的） | 实测 | 差 | 容差 |
| ---: | ---: | ---: | ---: | ---: |
| 10.5pt | 19.1100 | **19.1040** | −0.0060 | 0.0480 |
| 12.0pt | 21.8400 | **21.8400** | **0.0000** | 0.0480 |
| 16.0pt | 29.1200 | **29.1360** | +0.0160 | 0.0480 |
| 22.0pt | 40.0400 | **40.0320** | −0.0080 | 0.0480 |

N7 此前只是拉丁采集上的**回测**。这是它第一次在**新采集、新字体**上被预测检验，
四个字号全中。**但仍不能说那个 1.3 是代码页带来的**（判据 §2 已写明）：
本机没有能把「按代码页」与「按脚本」分开的字体——
「拉丁字形却声明东亚代码页」全机只有 Brush Script MT 一个（正是产生假说的那份数据里的），
「画得了 CJK 却不声明东亚代码页」**一个都没有**。**这是量具在本机的硬边界，不是没做。**

## 5.2 Z5：按字断行对上了，标点溢出边界没有

| 段落 | Word | 引擎 | |
| --- | --- | --- | --- |
| `wrapPlain`（不含任何标点） | `[37, 37, 33]` | `[37, 37, 33]` | **逐行相同** |
| `wrapKinsoku`（密布标点） | `[37, 37, 39]` | `[37, 37, 36, 3]` | **引擎多断一行** |

**CJK 按字断行本身是对的**——`font/linebreak.rs` 那套逻辑此前从未被任何读数碰过，
无标点段上它与 Word 逐行相同。

**差的是标点溢出边界。** Word 末行 39 个字形，行末 x = **538.30pt**，
而正文右边界是 523.20pt：`。` 的起点 523.33pt **已在边界之外**，段落标记的空格更在 535.30pt。
Word 宁可让收尾标点挂出去，也不为它换行；引擎把末 3 个字符推到了第四行。

这是 CJK 排版的一条具名规则（OOXML 的 `w:overflowPunct`，Word 默认开），
引擎**没有实现**。它与「行首禁则」是两条不同的规则，解法也不同：
禁则是把断点往**前**挪，溢出是允许行宽**超出**边界。

## 5.3 Z6：判不了，而且是判据自己预见到的

两段都是 **0/3** 行以禁则标点开头。按 §2 写死的对照说明，两段表现相同即判不了——
本夹具的换行点（第 37 个字）恰好从没落在标点之前，**禁则根本没有被触发过**。
要判它，得把标点精确摆在换行点上，那是下一份夹具的事。

## 5.4 引擎侧：横向已经对上，纵向的误差整个是那个 ×1.3

排除 p5（行数不同，无法逐字形配对）后 188 个字形：

| | |
| --- | --- |
| Δx max | **0.0005pt**（H6 的通道分辨率量级） |
| 行首字形 Δx 逐位相同 | **30/30** |
| Δy | 逐行累积，**增量恰好等于 N7 与 N1 之差** |

| 页 | 字号 | 逐行 Δy 增量 | N7 − N1 |
| --- | ---: | ---: | ---: |
| p1 | 12pt | −5.04 | 21.84 − 16.80 = **5.04** |
| p2 | 16pt | −6.72 | 29.12 − 22.40 = **6.72** |
| p3 | 22pt | −9.12 / −9.36 | 40.04 − 30.80 = **9.24** |
| p0 | 10.5pt | −4.32 / −4.56 | 19.11 − 14.70 = **4.41** |

**结论**：CJK 纯文本这条路上，引擎的横向（断行、推进量、行起点）**已经对上 Word**；
纵向的全部误差来自一件事——`RealMetrics` 用 N1 而 Word 用 N7，**少了那个 1.3**。

## 5.5 量具在这批里被改的地方

**F3 初扫命中 68 处**，全部是子集字体的 ToUnicode 反查不是单射：
汉字与它的康熙部首共用同一个字形，反查挑了部首那个码位
（`文 U+6587` → `⽂ U+2F42`、`行` → `⾏`、`一` → `⼀`…），
而且**只有本身是部首的那些字会中**，其余汉字一个都没错。

按 **Unicode 自己的兼容分解（NFKC）** 改身份核对的等价规则后归零，行分母一条不少。
不自己编表，是因为这层等价 Unicode 已经定义好了；实测 14/14 对上，
且 `文/丈`、`己/已`、`日/曰` 不会被弄混（回归测试两条，一正一反）。

**这条把方法 §3.1 的「ToUnicode 对 CJK 子集无效」从一句警告变成了有形状的东西**：
它不是随机失效，是**同形字共用字形时反查取了另一个码位**。
按 NFKC 归一之后，身份核对在 CJK 上**恢复可用**——
判据 §1 那张表里「CJK 没有身份核对」这一格，可以改写了。

另修：`fontcover.covered_chars` 不认 TTC，把 `Songti.ttc` 报成「一个汉字都画不出」。
方向是安全的（宁严勿松），但它会把正当夹具挡在门外。已按各 face 取并集，两条回归测试。
