## 0 为什么要这一份：把两件事分开

前六批一直卡在同一处，而卡住的原因是**两个变量从来没分开过**：

```
基线位置 = f(累加机制, natural)
```

每个候选形式都要先算 `natural`（过字体度量），所以「累加机制错了」与
「`natural` 算错了」在数据上无法区分。已经排除的（更细的整数单位、常数步长锚、
量化次序、`usWinAscent`、起页方式）都没能把它们分开。

`w:lineRule="exact"` 分得开：行距是**固定值**（`w:line` twips），
**与字体度量完全无关**。于是第 n 条基线的预测里只剩累加机制本身。

- **成立** → 累加机制（细累加 + 落位量化）**确立**，剩下的问题全在 `natural`；
- **判假** → 错的是累加机制，且**与字体无关**——那是比 `natural` 更深一层的东西。

两个结果都把问题砍掉一半。这是本批的全部用意。

## 1 容差

**0.0000pt**，逐位相等。唯一例外：PDF 读数的十进制舍入取 **1e-6 pt**。

## 2 预测

```
grid = 0.24pt，quantize(v) = 四舍五入(v / grid) × grid
step = w:line / 20  （twips → 点。exact 下这就是行距，与字体无关）
```

### X0 — 每条基线仍落在栅格上

**判为假**：任何一条基线不是 0.24pt 的整数倍。分母 = **360**。

这是第**七**次独立检验，而且是第一次在**非默认行距**下验——
前六批一律 `auto line=240`。栅格若只在单倍行距下成立，这一批就会露出来。

### X1 — 固定行距下的累加律（**本批的点预测**）

以每组**实测的第一条基线** `b₀` 为锚：

```
预测第 n 条基线 = quantize(b₀ + n × step)        n = 1 … 19
```

拿实测 `b₀` 当锚，是把首行那一项当已知条件给出去——首行是 V7，另案未决，
本批**只判累加**。一条预测只判一件事。

**判为假的读数**：任何一步 ≠ 预测值。分母 = **342**（18 组 × 19 步）。

## 3 夹具为什么这么排

- **`line` 值避开栅格的整数倍。** 0.24pt = 4.8 twips；`line` 若是 4.8 的倍数，
  每行都正好落在栅格上，「细累加」与「逐行各自量化」同解，白采。
  选的六个值（250 / 290 / 310 / 370 / 410 / 470 twips）除以 4.8 的小数部分
  依次是 .083 / .417 / .583 / .083 / .417 / .917。
- **每组 20 行。** 累加的差别是攒出来的（cursor-unit 的教训：一两步看不出来）。
- **字体在这一层上不是变量**——`exact` 下 step 与字体无关，所以复用第六批的三个族
  不违反 §7.2。用三个不同的族，反倒能顺带看「字体确实不影响 exact」。

## 4 采集前声明的排除项

某组的 20 行没有全部落在同一页上时，该组的 X1 读数**判不了**，记入分母但不算通过。
最大行距 23.5pt × 20 行 = 470pt，远小于正文高 698pt，正常排版下不该触发。

## 7 结论

采集包：`captures/exact-spacing-2026-09-17/`。Word for Mac，18 页，1440 字形，
前置核查 PASS，字体核查 PASS，四条证否条件一条都没触发。

| | 判据 | 结果 | |
| --- | --- | ---: | --- |
| **X0** | 每条基线落在 0.24pt 栅格上（非默认行距） | **360 / 360** | **成立** |
| **X1** | 固定行距下的累加律 | 300 / 342 | **不成立** |

### X0 成立：栅格在非默认行距下同样成立

前六批一律 `auto line=240`。本批六个 `exact` 行距值，**360 / 360**。
栅格不是单倍行距的特例。累计：**七份独立夹具、1906 条基线、零例外**。

### 分离成功：字体不参与

逐组得分，三个字体**一个数字都不差**：

| `w:line`（twips） | 250 | 290 | 310 | 370 | 410 | 470 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| Brush Script MT | 17/19 | 17/19 | 13/19 | 17/19 | 17/19 | **19/19** |
| Silom | 17/19 | 17/19 | 13/19 | 17/19 | 17/19 | **19/19** |
| Lao Sangam MN | 17/19 | 17/19 | 13/19 | 17/19 | 17/19 | **19/19** |

这正是本批要的：`exact` 下字体不参与行距，实测**完全**证实。
于是 X1 判假这件事，**与字体、与 `natural` 都无关**。

### X1 不成立 —— 这是把问题砍掉一半的那一半

**累加机制本身是错的。** 而且看清楚它错在哪一层：X1 的式子是

```
第 n 条基线 = quantize(b₀ + n × step)
```

- `b₀` 是**实测**的；
- `step = w:line / 20`，`w:line` 是整数 twips，**精确**，不过任何字体度量；
- `n` 是整数。

所以这个式子里**唯一还能错的只有 `quantize` 本身**——要么它的定义不对，
要么「位置由这个式子给出」这个前提不对。这是逻辑推论，不是从残差凑的。

残差**全部是 ±0.24pt，恰好一格**，没有一处两格。

### 对引擎的直接意义

引擎现在做的正是「细累加 + 落位量化」，也就是 X1 那个式子——**本批判假了它**。

但判假不等于知道对的是什么，所以引擎**这一轮仍不改**。
在知道正确形式之前动它，只会把一个错的换成另一个错的。

不过账要记清楚：此前三批的引擎改动（终止符字形、基线落栅格、步长不量化）
都还站得住——X0 连续七批成立，落位到栅格这件事没有被动摇；被判假的是
**落位之前那一步**怎么算。
