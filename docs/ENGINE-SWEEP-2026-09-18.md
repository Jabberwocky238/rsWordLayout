# 引擎 vs 全部采集包：第一次全量比对（2026-09-18）

**这份文件记的是引擎侧。** Word 侧的结论在
[`MEASUREMENT-BACKLOG.md`](MEASUREMENT-BACKLOG.md)，不在这里重复。

在此之前，`wm compare`（引擎轨迹 vs 采集包）只跑过 `MR1-BREAKS` 与 `accumulation`，
另外两份（`indent-align` / `hbox`）只读了比例与中位数。22 份采集包里**18 份从来没有引擎侧读数**。
`layout-trace` 在 `cf64f36` 把 rsword 钉到 `a8d24ea` 之后才重新编得出来，这一批是钉版之后的第一次。

**不驱动 Word。** 全部读数来自既有采集包与本地出的引擎轨迹。

轨迹一律用 `--metrics real --vertical-grid mac`，字体按每份采集包 `META.json` 的
`preflight.requiredFamilies` 装，`--require` 逐条核过。

## 1 量具自己被改掉的两处

两处都不是"改判据"：一处是检验的实现与它自己的文档不符，一处是方法 §3.1
早就写明不可靠的通道被当成了硬判据。**都在看数据之前就已经写死了该抓什么**，
这里改的是"怎么抓"。

### M-1 `selfcheck` 的「一行一条记录」把每一次换行都判成缺陷

判据本意（E-4）：一行被 run 切碎会出多条记录，行层配对必然失败。
实现却只查"同页内源区间接续上一条"——而**接续正是换行的常态**：
换行处被 trim 的空格留在上一行的源区间里（引擎与 Word 的逐页字形数逐份相等，
`hbox` p4 196=196、p5 324=324），于是下一行的 `sourceStart` 恰好等于上一条的 `sourceEnd`。

| | |
| --- | --- |
| 连排记录 | **2642 条**（22 份轨迹） |
| 其中同基线（真·按 run 切碎） | **0 条** |
| 其中异基线（换行，误报） | **2642 条** |

**旧判据在 22 份上全部误报**，连 E-4 当初判"已修、5/5 通过"的
`breaks` / `wrap` / `sample` / `complex` 也一起误报——那 5 份当初能过，
只是因为那时的引擎把换行空格丢在行外。

**修法**：接续**且同基线**才算缺陷。run 切碎出来的多条记录共用一条基线，换行的不共用。
一侧没有字形（空行没有基线）时记**判不了**，不当通过。
回归测试 `tests/test_selfcheck.py` 3 条，退回后误报立刻复现。

### M-2 身份核对的空白等价是单向的 —— 预注册的证否条件 F3 因此命中 442 行

`pairing` 的身份核对只认"PDF 侧解出 `" "`、源侧是空白"，不认反向。
实测 AppleMyungjo 的子集字体把段落标记那个空格字形的 ToUnicode 写成 `"\t"`：

| 采集包 | F3 命中行 | 形状 |
| --- | ---: | --- |
| shift-floor | 160 | 源 `\n` ↔ PDF 解出 `\t` |
| recursive | 160 | 同上 |
| page-start | 61 | 同上 |
| font-free | 40 | 同上 |
| noise-floor | 21 | 同上 |
| **合计** | **442** | **零例外，全部出自 AppleMyungjo** |

不含该字体的 17 份**一条都没有**。方法 §3.1 早写明 ToUnicode 对子集字体不可作依据，
只能当配对之后的核对手段——拿它去判空白字符的**类别**，判的是子集表，不是读序前提。

**修法**：两侧都是空白即不算不符。真配错字符仍抓（回归测试两条，一正一反）。

**这一条更要紧的部分不是修法。** 23 个预注册脚本各自有一个 `falsifiers()`，
扫的是 F-A（采前核查）/ F-B（字体替换）/ F-C（夹具身份）/ F-D（页集不符），
**方法的 F1–F4 一次都没进过判定**。所以 `VERDICT.json` 里那 22 个 `"falsifiers": []`
从来就不包含 F3——它不是"扫过且为零"，是"没扫"（§7.4：未核与核过无发现分两栏）。

修完之后重扫，**五份全部归零**，行分母一条不少
（font-free 240/240、noise-floor 63/63、page-start 322/322、recursive 320/320、shift-floor 320/320）。
所以 **V18 / V20 / H5 / V6 / V15 / V16 的判定不受影响**——那 442 条是子集表的伪影，
不是配对失败。但在今天之前，**这句话没有人核过**。

## 2 引擎对上了什么

| 层 | 读数 | 分母 |
| --- | --- | --- |
| **页数** | **逐份相同** | **20/20 份采集包** |
| 逐页字形数 | 逐位相同 | 15/20 份（差的 5 份见 §3） |
| **行首字形 Δx** | **0.0000pt 逐位相同** | **2395/2407 行**，16 份夹具 |
| 行末 Δx | ≤ 0.0004pt | exact-spacing / rounding / shift-floor / recursive / baseline-order |
| 行末 Δx | **0.0000pt** | accumulation（1340 字形，G-8d 的核过在另外 5 份上复现） |
| Δy | **全部落在 0.24pt 栅格的整数倍上** | 全部 13145 对 |

横向沿行的残余在 `accumulation` 上是 0.0225pt，正是 H6 那条通道分辨率，不是引擎的误差。

## 3 引擎侧缺口（量出来的，均未修）

### S-1 连字没关 —— 与 G-6 的字距调整同一根因

`rustybuzz::shape` 不传 feature 时默认开 `liga`。Word 没有用。

| 夹具 | 位置 | Word | 引擎 |
| --- | --- | --- | --- |
| font-free p3 L8 | Zapfino `di` | `d` `i` ` ` 三个字形 | 合成 1 个（glyphId 1080） |
| font-free p5 L5 | Trattatello `ff` | 三个字形 | 合成 1 个（glyphId 701） |
| font-free p5 L8 | Trattatello `fi` | 三个字形 | 合成 1 个（glyphId 702） |

后果与 kerning 同类，且**更隐蔽**：字形数变了，结构层就配不上，
差值里混进的是"少了一个字形"，不是几何误差。
G-4 修 kerning 时给了 `FontSpec::kerning`，连字没有对应的开关。

**顺带一条**：合成之后那一行**空格字形的 `sourceChar` 也跟着错**
（p5 L5 两个字形都报 165，空格本应是 167）——连字把源字符归属压平了。

### S-2 分页符的终止符标注错位一行

`breaks-sections` 33 行里 **12 行的标注与源字符不符**，三种形状：

| 形状 | 实例 | 引擎标注 | 该标 |
| --- | ---: | --- | --- |
| 段中分页符（`iz` + 分页符 + `w`） | 3 | 分页符之**前**那行标 `WRAP` | `PAGE_BREAK_*` |
| 同上，分页符之**后**那行 | 3 | `PAGE_BREAK_MID_PARAGRAPH` | `PARAGRAPH_MARK` |
| 分页符独占一段 | 3 | `PAGE_BREAK_MID_PARAGRAPH` | 三分里的 `OWN_LINE`（E-5） |
| 分节符行的区间漏掉段落标记 | 3 | 区间止于正文末，下一行从 +1 处起 | 待定 |

**前两种是同一个错**：段落里分页符**后面还有文字**时，标注整体挪到了下一行。
分页符在段末（`hy` + 分页符）时标注是对的。

这条不必等 Word 判——`selfcheck` 直接抓到 **3 行自相矛盾**：
记录自报该终止符产出 0 个字形，同一条记录里却画了 1 个（glyphId 88，就是正文的 `w`）。
这与 E-2 同形，但根因不同：E-2 是 U+FFFC 被画出来（已修），这条是标注挪了位。

### S-3 空段落与独占行的终止符空格没画出来

| 夹具 | Word | 引擎 | 差 |
| --- | ---: | ---: | ---: |
| breaks-sections | 90 | 75 | **15** |
| vmisc2 | 88 | 83 | **5** |

`vmisc2` p10：Word 画 `tail` ＋ 1 个空格（段落标记），引擎只画 4 个。
p7：Word 10 个 = 7 个正文 ＋ **3 个空格**（其中一个是 `TimesNewRomanPSMT`——
就是 vmisc2 测到的"Word 在默认字体里画空段落标记"），引擎只画 1 个空格。

正常正文行的段落标记引擎是画的（`a-form` 每行 3 个字形，第 3 个就是它，480/480 对上）。
缺的只在**空段落**与**终止符独占一行**这两种。这是 G-3 那条未决项的实测形状。

### S-4 字体名是「族名 + 字样」时选不中 face

`w:rFonts w:ascii` 里 Word 写的可以是**族名 + 字样**，而引擎只比 OpenType 的族名（name ID 1）：

| 夹具里的字体名 | 文件自报的族名(1) | 子族(2) | 结果 |
| --- | --- | --- | --- |
| `Bodoni 72 Smallcaps Book` | `Bodoni 72 Smallcaps` | `Book` | **选不中** |
| `Big Caslon Medium` | `Big Caslon` | `Medium` | **选不中** |

Word 选得中（采集里的 PDF 用的就是这两个 face）。引擎的 `select_face` 走
`env.select(&[family], …)` 带 fallback，选不中时**静默换一个能盖住码位的字体**——
而字体替换在几何上完全不可见（§6.2）。

**这次是 `--require` 把它拦下来的**，两份夹具（`first-line`、`cursor-unit`）因此**排不出轨迹**，
不是量具缺什么。没有这道闸门，它会安静地产出一份用错字体的轨迹。

### S-5 上下标字号落在整半点上

`prereg_engine.py` 第一次跑得起来（它要 `layout-trace`）。逐条套 `probe-metrics` 的判据：

| 预测 | 引擎 | 说明 |
| --- | --- | --- |
| P1 行高 = round(自然行高/0.24)×0.24 | **判不了** 16/28 | |
| P2 首行基线 = 行高 − round(descent/0.24)×0.24 | **OK 28/28** | 引擎实现的正是 W-2 那条**回测**式 |
| P3 上下标字号 = 0.66 × 正文 | **FAIL 0/6** | 10pt→**6.5**（预测 6.6）、12pt→**8.0**（7.92）、18pt→**12.0**（11.88） |
| P4 上标升 0.34 em / 下标降 0.08 em | **FAIL 0/6** | 偏 0.03~0.14pt，同一来源 |

P3/P4 的根因是 G-7 里已经写明的**单位天花板**：`FontSpec::size_half_points` 是整数半点，
0.66 × 12pt = 15.84 半点表达不了。这次量到了它在三个字号上的具体代价。

**P2 那条 OK 是要紧的**：它说明引擎的首行基线用的就是 W-2 的回测形式，
而 Word 侧 **V19 已经把四种形式全部排除**——所以引擎与 Word 在首行上必然分家，
分家的量见下。

### S-6 跨节边界的行距，引擎少一格

`probe-metrics` P5：常规行距 13.92pt，引擎跨节给 **13.68pt**，少 0.24pt。
Word 侧 `breaks-sections` S2 实测跨节增量**精确为 0.00**（两对读数），V11 已排除。
所以这里引擎与 Word 差**一整格**，方向还是反的。

## 4 剩下的 Δy 是什么形状

Δy 全部在栅格上（§2），所以问题只可能出在**落在哪一格**。逐页看：

| 夹具 | 每页 Δy 是常数？ | 各页 Δy（格） |
| --- | ---: | --- |
| noise-floor | **6/6** | 4, 12, −3, 4, 12, −3 |
| a-form | 10/16 | 20, 19, ×, ×, 14, ×, 10, ×, ×, 7, 6, ×, 4, 4, 3, 3 |
| fixed-distance | 11/16 | ×, ×, 24, 22, ×, 17, 16, 1, −1, −3, ×, ×, −13, −16, −19, −23 |
| indent-align | 12/20 | 后 12 页全 **0** |
| baseline-order | 15/24 | 15 页为 **0** |
| hbox | 8/10 | 8 页为 **0** |

`a-form` p0 是最干净的一页：**480 个字形里 p0 的 30 个，Δy 恒为 +4.8000pt = 整 20 格**，
行距两边都是 10.32pt，Δx 最大 0.0003pt。**步长对，起点差一个整格数**。
每页的偏移随该页的 `w:line` 变（20 → 19 → … → 3），这正是 V19 的形状：
**A 只依赖 `w:line`，而引擎用的 A（= S-5 的 P2 形式）是 Word 侧已排除的四种之一。**

**所以这条差不是引擎"写错了"，是 V19 本身没有答案。** 在想出下一个有原理的 A 之前，
引擎这边改任何一种形式，都只是把已经被排除过的东西换个数再排除一次
（`MEASUREMENT-BACKLOG.md` 收尾那段）。
