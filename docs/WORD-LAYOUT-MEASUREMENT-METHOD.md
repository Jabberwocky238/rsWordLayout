# 用真实 Word 验收排版引擎：量具方法

**给接手 Word 排版引擎开发的人。** 本文只写**怎么量**，不写某个仓库的流程。
所有数字都是实测得来的，每条都标了范围与分母；没测过的地方写「未测」而不是省略。

结论日期 2026-09-17。采集环境：Windows 桌面 Word 16.0.14334（主）、Word for Mac 16.112.26083020（辅）。

---

## 0 一句话

**不要试图测量 Word 的内部量（行基线、行盒、段间距分解）——那条路已经被证死。
改测每个字形被画在哪里：把引擎输出的字形原点，与 Word 导出 PDF 里同一字形的原点逐个相比。**

这个量具的噪声底是 **0.0000pt**（34 对同条件采集、38,845 对字形，逐位相同），
所以引擎跑出来的任何非零差值都是信号。

---

## 1 为什么不测行基线：这条路是被证死的，不是没试过

如果你的验收标准写成「行盒与基线误差 ≤ 0.5pt」，你会卡住。原因：

| 尝试过的通道 | 结果 |
| --- | --- |
| Word COM 对象模型的 `Line` 对象 | **不报基线**。只有 `Top`／`Height`／`Left`／`Width` |
| PDF 里的字形基线 | **不能唯一确定行基线**。同一份文档，`normal` 与 `flattened-raised` 两种排布下五个字形的 `yBaseline` **全是 300.0**，而真实行基线分别是 **300** 与 **304** |
| 段落边框 `pBdr`、下划线 `w:u`、相对行定位对象 | 三类都缺「从行边缘到行基线」的独立语义依据，无合格候选 |
| 带间距的行矩形分解成 before／文字行／after | 现有通道分不出边界；只能拿声明值去对，那是循环论证 |

**结论**：行基线与行盒的 ≤0.5pt 验收在现有通道上**不可测**（注意：是**不可测**，不是**无依据**——
这两件事完全不同，前者留着当未决项，后者才该删）。

**所以换问题**：不问 Word 内部怎么分解一行，只问每个字放在哪里。字形原点在 PDF 里是**直接可读**的量。

## 2 量具的两条通道

### 2.1 COM 对象模型（给结构）

`Application → Documents → Windows(1).Panes(1).Pages → Page.Rectangles → Rectangle.Lines`

每条 `Line` 给：`type`（0 = 文本行，1 = 表格行）、`Range.Start/End`（字符区间）、
`box.{left, top, width, height}`。另有 `Document.Paragraphs` 给每段的字符区间与文本。

**已标定**：`Line.Top` 是**整数点单位**读数，不是页面相对屏幕像素
（40 个观测：点单位整数化模型 40/40 相符，直接像素模型 0/40）。

**未标定**：`Line.Width` 含不含行尾空格、含不含缩进——**至今未定**，而它常被当主操作数用，小心。

**第三条独立通道**：`Range.Information(10)`（`wdFirstCharacterLineNumber`）返回某字符在本页的第几行。
实测 626 个不同的 (页, 行) 对，与 COM 的 626 条 `LineType=0` 记录数一致。用它交叉验证行划分。

### 2.2 PDF（给几何）

`Document.ExportAsFixedFormat` 导出 PDF，用 pdfminer 解析，逐字形取：
`glyphOrigin[x, y]`、`advanceVector`、`fontName`、`fontSize`、`text`、`textStatus`、`matrix`、`rise`。

**导出参数必须逐位显式传**，不要用默认值——默认里有会改变输出的项。
把用了哪个参数向量记进每次采集的记录。

## 3 核心难点：怎么把 PDF 里的第 N 个字形对上源文本的第几个字符

这是整个方法的关键，也是唯一需要动脑的地方。

### 3.1 不能靠 Unicode 身份

PDF 里的字形**可能没有 ToUnicode 映射**（合成字体、CJK 子集）。
即使有，简单 TrueType 子集经 WinAnsiEncoding 能给出字符身份（实测拉丁批次 111/111 `mapped`），
但这条路对 CJK 无效。**不要把它当配对依据，可以当配对之后的核对手段。**

**2026-09-18 补：它在 CJK 上怎么失效，量出来了。** 不是随机失效，是
**反查不是单射**——汉字与它的康熙部首共用同一个字形，子集的 ToUnicode
取了部首那个码位：`文 U+6587` 解成 `⽂ U+2F42`、`行` 解成 `⾏`、`一` 解成 `⼀`。
`cjk-plain` 采集里 68 处身份不符**全部**是这一形，且**只有本身是部首的那些字会中**，
其余汉字一个都没错。Unicode 自己定义了这层等价（康熙部首的兼容分解），
所以按 **NFKC** 归一之后再比，身份核对在 CJK 上**恢复可用**（14/14 对上，
且 `文/丈`、`己/已`、`日/曰` 不会被弄混）。

同一类还有一条：AppleMyungjo 的子集把**段落标记那个空格**解成 `"\t"`
（5 份采集包 442 行，零例外）。所以空白与空白之间也不该判不符。

### 3.2 按读序配对

同一行内，PDF 字形按内容流出现顺序编号 0..G−1；源字符按顺序编号 0..C−1；同序号相配。
**前提**：PDF 内容流的绘制顺序等于源字符顺序。这是一条新引入的前提，**必须显式写进验收定义**，
不能默认。

配对前做一次前置检查（逐行做，给分母）：

| 观察 | 处置 |
| --- | --- |
| G = 该行非空白字符数 | 空格不成字形，按去空格序列配对 |
| G = 该行全部字符数 | 空格也成字形，按全序列配对 |
| 两者皆非 | 该行**判不了**，记下 G 与 C，不猜 |

同一份文档里三种情形可能混着出现，**按行记，不按文档记**。

### 3.3 字形归到哪一行：按行盒纵向包含，不要按 y 聚类

把 PDF 字形原点的 y 用 `mediaBox` 高度翻转成页顶向下坐标，
落在 `lines[].box.top` 到 `top + height` 之间即归该行。

**不要按基线 y 做聚类**：有抬升 run（上标下标、`w:position`）的行会被拆成两簇。
实测 Δy = 4.08pt 就足以把一段拆成 2 簇，**且这个现象在 Windows 与 Mac 两个平台上都复现**。

八份采集实测：`outsideBox` 与重叠命中**全为 0**。

## 4 字形计数约定：Word 为每个看不见的字符画什么

**这是最可直接复用的产物。** 拉丁文本，简单 TrueType 字体。

| 源侧的东西 | Word 画几个字形 | 检验情况 |
| --- | --- | --- |
| 段落标记（`\r`） | **1 个空格** | 多份，Windows 侧 |
| 软回车（`w:br type="textWrapping"`，`\x0b`） | **1 个** | 03d–03h 30/30 |
| **分节符**（段内 `w:sectPr`，在 `Range.Text` 里也是 `\x0c`） | **0 个** | 88 站点实评 76、纯不符 0；但检验实例与设计实例同构，**结构性检验 Windows 侧为 0** |
| **手动分页符**（`w:br type="page"`）· 行首独占、自成一条行记录 | **0 个** | 同上，另 Mac 侧 4/4 |
| **手动分页符** · 紧跟段落标记 | **1 个空格**（该行连同段落标记共 +2） | Mac 侧 3/3，且由字形文本直接确认：`'B01 break before mark  '` 是 21 字符加两个尾随空格 |
| **手动分页符** · 段中（两侧都有文字） | **0 个** | Mac 侧 3/3 |
| 行尾／终止符前的尾随空格 | **照画**，个数不影响计数 | 11a 74/75、13a 16/16、03d/f/h 24/24 |
| 制表符（普通、竖线、连续、小数点） | **各 1 个空格** | 09a 15/15 行 |
| **前导符制表位**（dot／hyphen／underscore／heavy／middleDot） | 把**填充字符**画成一串普通文字字形，**另加 1 个空格**（填充串与标签之间） | 09a 30/30；heavy 与 underscore 共用填充字符 |
| **自动编号标签** | 画字形，但**源文本里没有对应字符**（`Range.Text` 里不存在） | 09a T8 3/3。取源候选是 `Paragraph.Range.ListFormat.ListString` |
| **行内对象**（图片等） | `Range.Text` 里 1 个占位字符，**PDF 里 0 个字形**，后续字形按对象宽度偏移 | n=1（60pt 图片对应 59.996pt 偏移） |
| 预期字形序列为空的行 | **0 个字形记通过**（空过） | 13a 1 处 |

**前导符的填充个数**：`n = floor(跨度 ÷ 步距)` **已被证否**（两个候选各 3/30）。
**步距本身已定**：就是该填充字符在字体里的 advance（30/30，最大差 0.0002pt）。
个数的正确公式**未知**，不要拿实测数据回归一个出来再说它是预测。

**目前仍在范围外**：制表符、跨页的表格行、自动编号、行内对象、合成字体（含 CJK 位图化）。

## 5 已经量出来的校准数据

| 量 | 值 | 范围 |
| --- | --- | --- |
| **同条件重复的噪声底** | `glyphOrigin` 的 max\|Δx\| = max\|Δy\| = **0.0000pt** | 34 对采集、38,845 对字形；同机、同 build、同字体 epoch、**同批次**。跨批次跨 build 未测 |
| 未进入行划分的字形 | **2,988 / 35,087 = 8.5%**，集中在抬升 run、脚注、表格页；其余 23 份夹具差 0 | Windows 总包 |
| 相邻字形错位的四分解 | A1 不构成错误 10,828／**A2 零实例 0**／B 3,777／C 仅身份核对能抓 1,064（6.8%）／未知 0 | 15,669 对 |
| 表格行 | 每行记录字符数稳定：`table0` 384/384（6 行 × 64）、`table1` 256/256（4 行 × 64） | **只在不跨页的表格行上**成立 |
| 脚注 | 正文行 9/9；引用标记 8.04pt 对正文 12pt、高 3.96pt、自成 y 簇；脚注正文 194/194；分隔线**无字形** | 1 份夹具 |

**噪声底是 0 这件事的意义**：你不需要给测量噪声留容差。引擎对 Word 出现任何非零差，
要么是引擎错，要么是配对错，不可能是「量得不准」。

## 6 会静默毁掉结果的坑

按踩过的顺序，每条都真实发生过。

### 6.1 Word 启动时缓存字体表

**装完字体必须重启 Word。** 而且**必须核 Word 进程自己能列出这些字体**——
不是核文件在不在，不是核别的进程看不看得见。

实测：16 个字体装于 11:28，Word 进程启动于两天前，结果 2618 条字形**全被替换**，
而 `system_profiler` 与文件检查都是通过的。

### 6.2 度量兼容克隆的字体替换，在几何上完全不可见

Liberation Serif 是 Times New Roman 的**度量兼容**克隆，Liberation Sans 对应 Arial，Carlito 对应 Calibri，
Caladea 对应 Cambria。**替换后几何一字不差**：

两批对照（一批被替换、一批没有），页数、mediaBox、逐页与总字形数、字形页归属、`text` 序列、
`fontSize`、**`glyphOrigin` 与 `advanceVector`**（2618 条记录，max |Δ| = **0.000000pt**）、
行号扫描、页行对分布——**全部相同**。只有字体子集名、PDF 字节与哈希不同。

**后果：任何几何自检都发现不了字体被换过，只有字体名能。**
检查字体文件集的哈希也挡不住——那检查的是机器上有什么，不是 Word 实际用了什么。

### 6.3 夹具「变体」往往共用同一份 document.xml

实测 63 份探针夹具只有 **41 份不同的 `word/document.xml`**，
12 个共用组覆盖 **34 份（54%）**，组内差别只在 `settings.xml`（兼容级与间距开关）。

**所以**：判 `document.xml` 构造的规则时，同组「变体」**不是检验实例**——它们与设计实例逐字节同构，
按构造不可能给出不同结论。**检验实例必须在被判的那一层上不同。**

（顺带一条真行为：**单独一个 `compatibilityMode` 15→14 就能把表格行拆到两页**，
同一份 `document.xml`。所以「对某开关不敏感」这种结论要写清楚说的是哪一维——
字形计数不敏感 ≠ 页面归属不敏感。）

### 6.4 不要从源侧推排版结果

踩过：预注册写「本件的表都不跨页，无跨页实例」——而跨不跨页是 Word 排出来的，源侧根本看不出来。

**凡出现「本件无 X 实例」，先问 X 是源侧可定的，还是排版结果。**

### 6.5 两份不同的文档之间，行级差值可能是 0

难例：两份计数层完全相同、只是行长排列不同的文档，比较时 3 行结构失败、
**剩下 1 行 8 个字形距离 0.0000pt**。

**报告必须先读 `state` 再读 `maxAbs`**，否则会把「配对失败」读成「完全一致」。
写进比较器的输出契约，不要只写进文档。

### 6.6 Mac Word 与 Windows Word 不能互相替代

- Word 在两个平台有**两套字体度量**（`usePre2018iOSMacLayout`）
- **Mac 没有 XPS 导出**
- Mac 的 AppleScript 桥缺术语，`Line` 返回 `Long` 且单位未映射——**拿不到行盒**，盒包含配对做不了
- Mac 通道的 PDF `fontSize` 逐条恒为 **1**（字号在文本矩阵里），**不可作字号读数**
- Mac Word 的文件授权**绑文件身份不绑路径**：同一路径换一份文件会重新弹授权框

**但**：拉丁文本的字形计数类结论（画不画、画几个）在两个平台上目前一致。
Mac 可以当便宜的先行探路通道，结论只能写「在 Mac Word 上观测到」。

## 7 让数字可信的纪律（这部分比方法本身更重要）

这套方法之所以能用，不是因为它精巧，是因为下面这几条把自欺堵死了。

1. **先预注册再看数据。** 判据、容差、**什么读数会让这条预测判为假**，写死并提交，再打开数据。
   把**判据的可执行形式（脚本）与判据文一起提交**——事后有没有动手，一条 `git diff` 就能核。
2. **设计案例不能兼作检验。** 用来形成规则的案例上它必然通过，那是构造不是证据。
   检验实例必须在**被判的那一层**上与设计实例不同（见 6.3）。
3. **三态出口**：成立／不成立／**判不了**。「判不了」这个出口不能取消，
   否则这套东西只会输出「成立」。**不许拿「未发现反例」代替「通过」。**
4. **每个数带分母**：N（范围内全部）／M（满足）／N−M（逐条列出不满足的）。
   「未核」与「核过无发现」分两栏——长得像，意思相反。
5. **看过数据后才成形的判据标「回测」**，不当独立检验。
6. **结论带范围**，范围与结论写在同一处，让下游没法只抄结论不抄限定。
7. **改结论时残差守恒**：原主张的每一条，要么留在新文本，要么转成具名未决项，
   要么给出「原本就无依据」的证据后删除——**没有第四种**。
   「降级为诊断项」这类说法就是第四种，会让义务悄悄蒸发。
8. **不可测 ≠ 从无依据。** 前者留着当未决项，后者才该删。这两件事分不清，
   验收标准会在一次「简化」里丢掉一半。

**一个实例说明第 1 条为什么值钱**：某次预注册时已经算出自己的预测与已知聚合值差 4，
也猜得到差在哪，但**没有改预测**。结果那条预测不中（预测 5 个字形，实测 1），
**而不中的那 4 个字形正好就是那个差额**。改过之后必中的预测，事后与没做预注册完全等价；
一条没改过的预测，不中的时候反而解释了别的东西。

## 8 目前还没解决的

诚实清单，别当成已完成：

- **个数公式**：前导符填充个数的公式被证否，没有替代。
- **仍在范围外**：制表符、跨页表格行、自动编号（缺采集字段）、行内对象（n=1）、合成字体与 CJK。
- **8.5% 的字形不在验收覆盖内**——目前的处理是**显式写进验收定义里排除**，不是给出归属。
  给归属要靠表格与脚注的行级约定，而那两件都只在有限范围内成立，现在给归属等于拿未终态的约定去撑全称。
- **行盒（O-30）与行基线（O-31）**：转成未决项，未解。
- **跨批次、跨 build 的重复性**未测；噪声底 0.0000pt 只在同批次内成立。
- **A2（几何可抓的错位）零实例**：需要一份行内混字体／字号的夹具才能检验。

## 9 如果你从零开始搭这套东西

按这个顺序，每一步都能独立验收：

1. **采集链**：Word COM 读 `Pages → Rectangles → Lines`，导出 PDF，两者进同一个包，
   包里记环境指纹（Word build、**字体文件集哈希**、dpi、zoom、区域）。
2. **前置核查**：采集前核 **Word 进程自己**能列出所需字体（§6.1）。这道核查是唯一防线。
3. **重复性对照**：同一份夹具同条件采两次，比 `glyphOrigin`。应当逐位相同。
   **不相同就先别往下走**——那说明采集链本身不确定。
4. **配对器**：按 §3 实现，先跑正对照（同条件两次采集，预期 Δ = 0）与
   阴性对照（两份不同夹具，预期配对失败）。四条证否条件一条都不该触发。
5. **计数约定**：按 §4 的表实现，逐行报 `COUNT_OK` / `COUNT_MISMATCH` / 判不了。
   新加一条约定就按 §7 的纪律走一遍。
6. **比较器**：页 → 行 → 字形三层配对，任何一层数目对不上即**结构失败，不修配对再比**；
   判定用欧氏距离；输出先给 `state` 再给 `maxAbs`。
7. **接引擎**：引擎输出要给每页、每行、每字形的原点与推进、所属源字符区间、行终止符类型。
   这是比较器的输入契约，越早定越省。
